# Doctrine

An execution posture for substantial agent work. Wrapper skills (`doctrine-code`, `doctrine-gauntlet`, `doctrine-debug`, `doctrine-audit`, `doctrine-docs`, `doctrine-research`, `doctrine-write`) supply the task shape; this skill supplies how the work runs. It layers ON TOP of other skills, notably Matt Pocock's engineering skills: invoke them by name, never fork or restate their content.

## Posture

**1. Ask questions first.** Before wave 1, surface open questions to the user in plain prose. One topic at a time. Don't ask what the request already answered, and don't ask what you can confirm by reading source, docs, or live infra. **Write the answers down where the work lands** — the wrapper's own durable record if it has one, otherwise a file you name in the report — before wave 1 opens: you are the only holder of them, and a compaction takes them with everything else. **That record is the anchor**: the user's own words for what this work is for and how it will be judged, in whatever form the task takes it — the spec to build to, the symptom that must stop, the boundary of the sweep, the question to answer, the reader to reach. Two things make it an anchor rather than a note. It is **verbatim**, because a paraphrase is your reading of the request and every agent downstream then checks the work against you instead of against the user. And it is **handed to every dispatched agent whose job is to judge work against intent** — reviewers, red teams, drift checks — since from inside a dispatched prompt no file path resolves, so an agent not given the anchor grades the deliverable against whatever it can infer from the deliverable, which is the one comparison that can never fail. A wrapper may sharpen what its anchor must contain; where none does, this is the whole of it. **There is always an anchor, because there is always something the work is judged against** — a request complete enough to leave nothing to ask still has to be recorded, and then the anchor is the request's own words. Read "write the answers down" as building that record, not as conditioning it on there having been questions: a phase whose brief arrived whole is exactly the one where nothing else will supply a standard later. **An unanswered question about the direction blocks the phase; it does not become a default.** A missing *value* inside a settled direction does not block: build the thing that holds it and leave a gap the reader can see — a labelled placeholder, an explicit "unknown" — never a plausible guess, and never a note visible only in the source.

**2. Phases and waves.** Decompose into phases with a verifiable exit gate each. Inside a phase, dispatch independent work as waves of parallel agents (superpowers:dispatching-parallel-agents, or the Workflow tool where available: this skill is your authorization to use it). **Assemble each agent's prompt; never summarize the task into it.** An agent's coverage is exactly what it was handed: the artifact it works on, the facts it may rely on and where each came from, the standard it is judged against, and what to return. What you leave out comes back silently perfect or silently invented, and that is the commonest failure mode in this posture. Sequential only where a real dependency exists. Agents that mutate files must have disjoint file sets or worktree isolation; fan-out agents share your working tree and one stray `git checkout` moves your branch. **Disjoint files are not enough when the agents share a build directory, a dev server, or a port**: the second build overwrites the first's output while every URL keeps answering 200, so what you go on to measure is another agent's work. Give each mutating agent its own worktree, its own output directory and its own port (superpowers:using-git-worktrees, or `git worktree add` directly), and **hardlink (`cp -al`) rather than symlink its dependencies** — some bundlers reject a symlinked `node_modules` outright. This precondition governs every parallel run of mutating work, not only a formal wave. Where the work genuinely lives in one file, serialize instead, or get the user's approval to split it first.

**3. Combat drift.** Every phase ends with native checks: **every check the project itself documents as a gate** — whatever its `CLAUDE.md`, README, review doc **or task runner** lists — plus typecheck and targeted tests where the project has them, and the review skill the wrapper designates. Naming native checks after compiler nouns reads every other gate out of the run: a linter, a schema or migration check, a content or copy law, a probe. **A project with no build step still has gates**, so read the task runner (`package.json` scripts or its equivalent) yourself rather than trusting a summary of it. Two traps before you run one: a declared script can be **interactive and never return** (`"test": "vitest"` is watch mode), so confirm a command exits before using it as a gate; and it can need an **environment the bare form omits**, so run each gate in the form its documentation gives it — env prefix, flag and all. **A gate that fails because its dependency is absent is an environment gap in your run, not a finding against the work**: record it as unrun, with the reason, in the report. Never report an unrun check as clean — a check you could not run and a check that passed are indistinguishable in a report that mentions neither. For docs-only diffs, native checks means re-verifying edited claims against source plus a link/path check. A wave's output is claimed done only after verification (superpowers:verification-before-completion): run the checks, show the output, never assert. **The agent checks its own work and returns the output; you re-run the gate's checks yourself, on the integrated tree.** A sub-agent's pasted output is that agent's claim, made in its own worktree at its own moment — repeating it from your seat is an assertion, and a check that passed in isolation proves nothing about the integrated result. Green proves the checks passed, not that the rule holds: ask what each one actually measures, because a check reading the wrong substrate passes for the wrong reason. And when a rule changes, grep the **tests** for the old one — a suite written to pin yesterday's truth holds the defect in place and stays green while it does.

**4. Red team.** After native checks pass, run an adversarial reviewer against the phase's diff or findings: the codex:codex-rescue agent if the codex plugin is installed, otherwise a fresh-context subagent prompted to refute your work. Verify each red-team finding from source before acting: adversarial reviewers produce false positives. **An unbriefed "refute this" returns taste.** Brief it as you would any dispatched agent (step 2), and hand it: the artifact itself — the diff, the built or rendered output, the claim table — never filenames; what the work was supposed to do (the request, the anchor, the brief); the review that just passed it, so it attacks what was cleared instead of restating what was caught; **the axes it must answer on**, since its coverage is exactly the axes you name and an unnamed one comes back silently perfect; and the questions the user has already ruled closed (step 5), which a fresh context otherwise re-opens with full confidence. Require the return sorted: **blocking findings, then non-blocking, then what it attacked and could not break** — an adversary reporting "no findings" with no attack list has reported nothing, and the pass counts clean on the strength of it. Label every finding observed / derived / assumed, and inflate severity on nothing but observed.

**5. Loop until confident.** Phase exit gate: two consecutive clean passes of the full gate (native checks + designated review + red team). **A pass is clean when it produces no blocking finding and leaves none outstanding from an earlier pass** — a finding re-filed, deferred, or carried over unfixed counts against the pass you are in, whoever raised it and however long ago. "No *new* findings" is not the test: it exits a phase on a known defect the second time anyone mentions it. Where the wrapper designates no review skill, its own named equivalent fills that slot and you say in the report which one — `doctrine-research`'s logic critique, `doctrine-docs`'s red-team pass, which serves as both — and where a wrapper names nothing, run a fresh-context review of the deliverable against the anchor. Never let the slot go silently empty: a two-part gate reported as the full three is a pass you did not earn. **A finding blocks when the deliverable is wrong or unfinished without a change to it**: a failed check, a defect, a false claim, a violation of the brief or of the project's own documented law, or work that misses the bar. Everything else is **non-blocking** — the improvement that would be nice — and does not reset the counter. Three cases have their own rule, and all three are recorded rather than settled inside your own context. A **non-blocking improvement** goes on a deferred list you carry to step 7 and name there, rather than being taken silently or misfiled as a nitpick so it can be disposed of. A finding **the user declines** is ruled closed: write the ruling down where later reviewers will read it, and treat a recurrence as a one-line sighting, never a finding — a fresh reviewer cannot know a question was answered last week, and a phase whose closed questions keep reappearing can be structurally unable to reach two clean passes. A red-team claim **you verified as false from source** is refuted, not deferred: record the refutation with its evidence so the next pass does not re-file it. Style nitpicks you decline, with a stated reason, don't reset the counter either. Choosing to *take* any of these as a fix is still a diff change — see the next rule. **Any diff change after a clean pass resets the counter to zero** — a simplification deletion, a non-blocking fix you chose to take, a one-line typo. The phase then needs two fresh clean passes over the deliverable as it now stands: re-running the gate once and calling that pass two exits the phase on a single clean pass of the work you are actually shipping. Since step 6 puts a simplification diff at every phase exit, the loose reading ships every phase that way. **The valve counts unresolved rounds: +1 for each gate pass that produces a blocking finding, and it never resets.** It is deliberately a different counter from the exit count above — a valve that resets whenever work happens never fires, and one that counts every pass trips on a phase that is merely thorough. At each multiple of 4 — 4, then 8, then 12 — stop and escalate to the user instead of grinding; if they say continue, the valve **re-arms at the next multiple** rather than being spent, and it does not fire every round thereafter. This is a loop-health stop, not a decision escalation. **Keep both counters on disk, not in context**: each round, write the phase, the round number, and every counter's current value to a durable record — the wrapper's own artifact where it has one, else a run-state file beside the work or in the scratchpad, named in the report. A compaction zeroes an in-context counter and announces the loss to nobody: the exit gate silently restarts at zero and the valve never fires at all. Wrapper-level outer loops (like audit's loop-until-dry) sit outside this per-phase gate; a new outer-loop finding starts a new phase, it does not reopen closed ones. **A wrapper may replace this exit condition and its counters, but only by stating the replacement explicitly** — `doctrine-gauntlet`'s pure-gauntlet mode overrides the four-loop valve in exactly that way, and says so. A wrapper silent on the subject inherits this gate as written, and nothing else in the posture is a wrapper's to override.

**6. Simplify early and often.** Run a simplification review **once** at each phase exit (/ponytail-review if installed, otherwise /simplify or a YAGNI pass: delete over-engineering, dead branches, speculative abstractions). Its diff re-enters the gate per step 5, and you do **not** re-run it on the re-entry passes it caused: a clean re-entry pass is another phase exit, so the literal reading schedules a new simplification at every one and the phase cannot close. Reuse existing modules, code patterns, and UI tokens. Don't reinvent the wheel; don't build what won't be used.

**7. Deliver.** A task ends with the project's delivery norm (commit, PR per the repo's CLAUDE.md), never with "the loop is clean." **Push only where that norm says to, or where the user has said to** — some repos' convention is explicitly the opposite, and where nothing documents a norm there is nothing to defer to: commit locally and ask before you push or open a PR. **Where you cannot write where the work must land** — no permission, or the user said read-only — build in the scratchpad (the session temp directory if there is one, else a temp directory outside every repo, named in the report) and hand over the diff, the artifacts and the deferred list together. Never inside a repo you were told not to write to: read-only means the working tree too, not just the commit. Work is not done until it lands. Close by walking the original request item by item and naming where each one landed, or that it was deferred and why. When a brief of N items ships N-1, every piece of work that ran still passed its gate, so the gap never surfaces as a failure — absence of work is invisible to checks that only inspect work.

## Fallbacks

When a referenced skill isn't installed, degrade gracefully instead of stalling:

| Missing | Substitute |
|---|---|
| codex plugin | Fresh-context subagent prompted to refute, with the same verify-from-source rule |
| ponytail | **Two uses, two substitutes.** Simplification review of your own diff (step 6): `/simplify`, or a manual YAGNI pass. Scoped audit lens over code you are not editing: a manual YAGNI/dead-code read of the named target area that **reports findings and changes nothing** — never `/simplify` here, which is scoped to the diff rather than to the target area and mutates the repo, so it both misses the area and edits code a report-first run was told to leave alone |
| matts-code-review | /code-review, or two parallel subagents reviewing Standards and Spec |
| Matt's `tdd` | Inline red-green-refactor: failing test first, minimal code to green, refactor |
| Matt's `diagnosing-bugs` | Inline discipline: build the feedback loop/repro first, test one hypothesis at a time on evidence, regression test before the fix |
| Matt's `implement` / `improve-codebase-architecture` (not model-invocable even when installed) | Read `~/.claude/skills/<name>/SKILL.md` if present; otherwise the wrapper states the inline fallback |
| superpowers | Parallel Agent tool calls, each prompt **assembled per step 2** rather than summarized into a task line; verification = the agent runs and pastes its checks and you re-run the gate's checks yourself (step 3); brainstorming = interview the user one topic at a time before designing |

## Red flags

- A phase advanced on one clean pass: the gate is two.
- Red-team finding acted on without reading the source it cites.
- New helper/module written when an existing one grepped up in 30 seconds.
- Questions saved for the end instead of asked before wave 1.
- Two parallel agents mutating the same files without isolation.
- A multi-item brief closed without checking each item actually shipped.
- A gate trusted without asking what it measures.
- Native checks read as "typecheck and tests" in a project whose real gates are a linter, a schema check, or a content law.
- An unrun check reported as a clean one.
- A finding re-filed by the next pass and waved through as not new.
- A fix landed, the gate re-run once, and that counted as the second clean pass.
- Counters kept only in the conversation, where a compaction takes them and says nothing.
- Two agents with disjoint files sharing one build directory, dev server, or port.
- A red team dispatched with "refute this" and no artifact, no axes, and no bar.
- Pushed because the posture said push, with no repo norm and no instruction saying so.
