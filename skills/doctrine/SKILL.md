# Doctrine

An execution posture for substantial agent work. Wrapper skills (`doctrine-code`, `doctrine-gauntlet`, `doctrine-debug`, `doctrine-audit`, `doctrine-docs`, `doctrine-research`, `doctrine-write`) supply the task shape; this skill supplies how the work runs. It layers ON TOP of other skills, notably Matt Pocock's engineering skills: invoke them by name, never fork or restate their content.

## Posture

**1. Ask questions first.** Before wave 1, surface open questions to the user in plain prose. One topic at a time. Don't ask what the request already answered, and don't ask what you can confirm by reading source, docs, or live infra. **Write the answers down where the work lands** — the wrapper's own durable record if it has one, otherwise a file you name in the report — before wave 1 opens: you are the only holder of them, and a compaction takes them with everything else. **That record is the anchor**: the user's own words for what this work is for and how it will be judged, in whatever form the task takes it — the spec to build to, the symptom that must stop, the boundary of the sweep, the question to answer, the reader to reach. Two things make it an anchor rather than a note. It is **verbatim**, because a paraphrase is your reading of the request and every agent downstream then checks the work against you instead of against the user. And it is **handed to every dispatched agent whose job is to judge work against intent** — reviewers, red teams, drift checks — since an agent not given the anchor grades the deliverable against whatever it can infer from the deliverable, which is the one comparison that can never fail. A wrapper may sharpen what its anchor must contain; where none does, this is the whole of it. **There is always an anchor, because there is always something the work is judged against** — a request complete enough to leave nothing to ask still has to be recorded, and then the anchor is the request's own words. Read "write the answers down" as building that record, not as conditioning it on there having been questions: a phase whose brief arrived whole is exactly the one where nothing else will supply a standard later. **An unanswered question about the direction blocks the phase; it does not become a default.** **A question is about direction when nothing but the user can answer it and the work is aimed differently depending on the answer.** Where the source answers it, it is a lookup and you do the lookup rather than blocking on a question you could have closed yourself. Where several answers are defensible and the deliverable is acceptable under each, it is a scope edge and not a direction question: take the narrower reading of **what you change** and the wider of **what you examine** — an unwanted edit is what somebody has to undo, an unexamined site is what nobody ever finds, and that is the same split step 5's class sweep makes. **The wider half covers examination that costs only time**: more source, more docs, more history. A broader query against live infrastructure can cost money, add load to a system in use, or reach data this run was never granted, and there the default is the narrower examination, not the wider. Then record the choice, the alternatives you rejected and why, and carry it to step 7 so the user can widen it. Blocking a phase on a scope edge costs the whole run and returns nothing; defaulting on a direction question ships work aimed at a guess. **Where you cannot tell which it is, it is a direction question and it blocks.** The two failures are not symmetrical: a phase blocked in error is visible, costs a question and resumes, while a narrowing made in error ships a coherent deliverable aimed at the wrong reader or tree, and every seat that follows inspects the slice you chose. A missing *value* inside a settled direction does not block: build the thing that holds it and leave a gap the reader can see — a labelled placeholder, an explicit "unknown" — never a plausible guess, and never a note visible only in the source.

**2. Phases and waves.** **Bound a phase downward as well as up, and settle it while decomposing, before any phase opens.** Step 5 runs its seats over the work twice, so the smallest phase costs close to what a large one does; the frontmatter's exclusion of one-off questions and single-file edits governs whether this skill fires at all, and nothing re-checked scale after a wrapper had already fired on task type. **Judge the work by its reach, never by its size**: a one-line change to a gate law, a shared contract, or this posture itself has the widest blast radius there is and earns the full gate outright, while a mechanical sweep across files nothing else reads may not. **Reach is what you went and looked for** — the callers, readers and consumers you actually searched — and where the search comes back inconclusive the work keeps the gate, because the branch that sheds it is the one an agent under time pressure wants to reach and the seats it sheds are the ones that would have found the reach. Work whose reach you have *shown* to be small folds into a neighbouring phase and rides its gate: not a skipped gate, one paid once rather than twice. Folding is a decomposition-time move only — a phase that has already opened carries counters, and folding it into a neighbour would launder them. Where nothing neighbours it, say so and do the work, still under step 3's native checks and one review of the finished result, which is the floor rather than nothing. Then decompose into phases with a verifiable exit gate each. Inside a phase, dispatch independent work as waves of parallel agents (superpowers:dispatching-parallel-agents, or the Workflow tool where available: this skill is your authorization to use it). **Assemble each agent's prompt; never summarize the task into it.** An agent's coverage is exactly what it was handed: the artifact it works on, the facts it may rely on and where each came from, the standard it is judged against, and what to return — for a seat that builds or mutates, including the output step 3 requires it to paste. What you leave out comes back silently perfect or silently invented, and that is the commonest failure mode in this posture. Sequential only where a real dependency exists. Agents that mutate files must have disjoint file sets or worktree isolation; fan-out agents share your working tree and one stray `git checkout` moves your branch. **Disjoint files are not enough when the agents share a build directory, a dev server, or a port**: the second build overwrites the first's output while every URL keeps answering 200, so what you go on to measure is another agent's work. Give each mutating agent its own worktree, its own output directory and its own port (superpowers:using-git-worktrees, or `git worktree add` directly), and **hardlink (`cp -al`) rather than symlink its dependencies** — some bundlers reject a symlinked `node_modules` outright. This precondition governs every parallel run of mutating work, not only a formal wave. Where the work genuinely lives in one file, serialize instead, or get the user's approval to split it first.

**3. Combat drift.** Every phase ends with native checks: **every check the project itself documents as a gate** — whatever its `CLAUDE.md`, README, review doc **or task runner** lists — plus typecheck and targeted tests where the project has them, and the review skill the wrapper designates. Naming native checks after compiler nouns reads every other gate out of the run: a linter, a schema or migration check, a content or copy law, a probe. **A project with no build step still has gates**, so read the task runner (`package.json` scripts or its equivalent) yourself rather than trusting a summary of it. Two traps before you run one: a declared script can be **interactive and never return** (`"test": "vitest"` is watch mode), so confirm a command exits before using it as a gate; and it can need an **environment the bare form omits**, so run each gate in the form its documentation gives it — env prefix, flag and all. **A gate that fails because its dependency is absent is an environment gap in your run, not a finding against the work**: record it as unrun, with the reason, in the report. **A gate already failing at the revision your work started from is attributed, not waived.** Run it, record its status every round, and record that it was red at the fixed point with the evidence — the same command on the untouched revision, compared on **which checks failed and not merely on whether the command did**: a runner that stops at the first failure hides every later one behind it, so two identical red exits can mean two different sets of broken checks. Where the runner will not show you the rest, attribution reaches only the failure you can actually see, and the checks behind it did not run: record them as unrun with the reason, exactly as above, rather than letting the attribution cover them. Rerunning reproduces the same stop, so another round never surfaces them and the phase would otherwise sit *Open* with nothing to advance it: put them to the user as a ruling in flight, the way an untestable site does below, rather than certifying a pass over checks nobody has seen. That attributes the failure to the tree you inherited rather than to this phase, and attribution is the whole of what it buys: the check has not become unrun, it has not stopped being a failed check, and it still appears in what shipping now would mean (step 5), including any rule of the project's own that blocks landing while it is red. What changes is only whose finding it is, and that is what settles the gate: it **does not block, does not reset the exit count, and does not hold up step 4's red team**, because no change to the deliverable could clear it, and a gate correct work cannot satisfy is broken — the test this posture applies to a project's gates and must apply to its own. Read step 4's "after native checks pass" as the checks this work is answerable for. A phase is never *Unable* on its account either, because it ran. Two things void the attribution: your diff makes it fail differently or fail more, and the wrapper or the user has put that gate inside the deliverable — then it is yours. And a gate red at the fixed point that this work was supposed to turn green is not attribution at all; it is the work. Never report an unrun check as clean — a check you could not run and a check that passed are indistinguishable in a report that mentions neither. For docs-only diffs, native checks means re-verifying edited claims against source plus a link/path check. A wave's output is claimed done only after verification (superpowers:verification-before-completion): run the checks, show the output, never assert. **A gate passes on its exit status; the output is what you show for it, not what you judge it by.** A command that ran nothing exits non-zero and prints something that reads like success — a runner that collected no tests, a script whose module failed to resolve, a suite that matched no files — so read the status, and where a runner can exit 0 having collected nothing, read the count it collected too — **and a gate that exited 0 having collected nothing is a failed check, not a pass**: it measured your work exactly as thoroughly as never running it, so it blocks like any other failed check until it collects something or the wrapper rules it waived. This is none of the cases beside it: nothing was absent, it did run, and it was not red before you started. **The agent checks its own work and returns the output; you re-run the gate's checks yourself, on the integrated tree.** A sub-agent's pasted output is that agent's claim, made in its own worktree at its own moment — repeating it from your seat is an assertion, and a check that passed in isolation proves nothing about the integrated result. Green proves the checks passed, not that the rule holds: ask what each one actually measures, because a check reading the wrong substrate passes for the wrong reason. And when a rule changes, grep the **tests** for the old one — a suite written to pin yesterday's truth holds the defect in place and stays green while it does.

**4. Red team.** After native checks pass, run an adversarial reviewer against the phase's diff or findings: the codex:codex-rescue agent if the codex plugin is installed — it **forwards to the Codex CLI and usually returns only a start line, with the review itself in the job record**; retrieve that record and read the sorted return out of it before the seat counts at all — a start line carries no findings and no attack list, and counting one is the empty-seat failure this step exists to stop. **A seat that returns a handle has also taken the work off screen, so make the job visible before you start waiting.** That same record carries the live log the job is writing as well as its status and pid — `codex:codex-rescue`'s backing companion reports `logFile` alongside `status` and `pid` from one `status <job-id> --json` call — so where the run sits inside herdr (`HERDR_ENV` is `1`), split a labelled pane and tail that log in it for as long as you wait. A foreground seat returns nothing until its job ends, so the id is not in your hands when you need it: the newest `jobs/*.json` under the companion's state directory for this workspace (`~/.claude/plugins/data/codex-openai-codex/state/<workspace>-<hash>/`) is the job you just started — check its `createdAt` against your dispatch time and its `summary` against your brief's opening words, since another dispatch in the same workspace can land a record between the two — and that is where to read it from. The seat's own pane dies with the seat, which is a minute in and often forty before the job ends: a wave whose only remaining sign of life is an orchestrator polling looks exactly like a hang, and a user who cannot see the work has no way to tell a long review from a dead one. Display only, on the same terms as step 5's sidebar token: outside herdr it is skipped in one line, and a split or tail that fails is noted and ignored — never blocking the pass, resetting a counter, or spending one of the seat's retries. Retrieved, it is a returned seat costing no retry, not a failed one; pick any seat by what its contract says it does, and where the only one available does something else, say so in the report, otherwise a fresh-context subagent prompted to refute your work. Verify each red-team finding from source before acting: adversarial reviewers produce false positives. **An unbriefed "refute this" returns taste.** Brief it as you would any dispatched agent (step 2), and hand it: the artifact itself — the diff, the built or rendered output, the claim table — never filenames; what the work was supposed to do (the request, the anchor, the brief), **pasted verbatim and never as a path**, since a seat pointed at a file reads its own summary of it, and of a hundred and eleven sampled briefs not one carried the user's words; **the whole blocking definition from step 5 in its own words** — the test, the three buckets and the steering-role rule — because a seat handed only the list of instances files every imprecise sentence as a false claim; the review that just passed it, so it attacks what was cleared instead of restating what was caught; **the axes it must answer on**, since its coverage is exactly the axes you name and an unnamed one comes back silently perfect; the questions the user has already ruled closed (step 5), which a fresh context otherwise re-opens with full confidence; and **its own bound, the non-mutating rule below, stated in the brief** — it binds the seat, and a seat never told it will helpfully edit. Require the return sorted: **blocking findings, then non-blocking, then what it attacked and could not break** — an adversary reporting "no findings" with no attack list has reported nothing, and the pass counts clean on the strength of it. Label every finding observed / derived / assumed, and inflate severity on nothing but observed. **A reviewer seat is non-mutating**: it reports and quotes diffs, it never applies them — a reviewer that changed the artifact has voided the substrate of the pass, which reruns on a restored or new revision. (A gate item that *builds* something — a consumer build, a render — is a check, not a reviewer.)

**5. Loop until confident.** Phase exit gate: two consecutive clean passes of the full gate (native checks + designated review + red team). **A pass is certified against one identified artifact revision**: every seat runs against it, and a change to the artifact before every seat has returned voids the pass and opens another on the revision as it now stands — whatever already came back reviewed something that no longer ships. **A pass is clean when it produces no blocking finding and leaves none outstanding from an earlier pass** — a finding re-filed, deferred, or carried over unfixed counts against the pass you are in, whoever raised it and however long ago. "No *new* findings" is not the test: it exits a phase on a known defect the second time anyone mentions it. Where the wrapper designates no review skill, its own named equivalent fills that slot and you say in the report which one — `doctrine-research`'s logic critique, `doctrine-docs`'s red-team pass, which serves as both — and where a wrapper names nothing, run a fresh-context review of the deliverable against the anchor. Never let the slot go silently empty: a two-part gate reported as the full three is a pass you did not earn. **A finding blocks when someone acting on the deliverable as it stands would do the wrong thing** — the deliverable, not the paperwork about it. That test comes first, and the instances follow from it: a failed check, a defect, a false claim about what the product does in an artifact that ships (the code, its tests, user-facing docs, the spec's behaviour clauses, an ADR's decisions, and a comment or docstring that describes product behaviour, since the next engineer acts on those), a violation of the brief or of the project's own documented law, a required seam with no test, or work that misses the bar. **You apply that definition, not the seat that filed the finding**: a seat sorts and labels its return, and you grade every item against the test in both directions — a claim you verified false from source is refuted whatever the seat called it, and a claim you verified true that leaves the deliverable wrong blocks however the seat labelled it. **Three things never block, whatever a seat calls them.** A statement about the gate's own instruments and history — a count, a coverage claim, a round number, what a test guarantees, a "verified by" note, a commit message — because nobody acts on it and it rots every time the work moves. Wording whose meaning is correct, however imprecise. And any artifact **in its steering role**: the spec, the anchor, the decision log and the record are how the run steers itself, and a wrong sentence in one of them is corrected where it sits, because the gate exists to certify what ships; the same file blocks where it *is* the deliverable, as a written spec or a report is. **Findings come in three buckets, not two.** Blocking, as above. **Non-blocking**: the improvement that would be nice, or a finding you cannot yet grade, which goes on a deferred list you carry to step 7 and does not reset the counter. And **not a finding**: wording that fails the consequence test and changes neither what the code does nor what it is for — a rename touches the code's text and not its behaviour, and the test is the consequence, never the file the sentence sits in — which is not filed at all — not as a nitpick, not on the deferred list — because a list of such items is noise that hides the signal. Precedence runs from the test, never from the artifact type: a comment that would send its reader wrong is blocking however cosmetic it looks, a seat drops only what it is sure fails the test, and files what it is unsure of as non-blocking for you to grade. Put the definition — from "A finding blocks" through the seat's unsure rule just above, and nothing after it — in every reviewer's brief (step 4): a seat handed only the list of instances files every imprecise sentence as a false claim, and in three live repos that is what the owner was asked to narrow at valve after valve. Three cases have their own rule, and all three are recorded rather than settled inside your own context. A **non-blocking improvement** goes on a deferred list you carry to step 7 and name there, rather than being taken silently or misfiled as a nitpick so it can be disposed of. A finding **the user declines** is ruled closed: write the ruling down where later reviewers will read it **and put it in every reviewer seat's brief, not only the red team's** — step 4's hand-list carries the closed questions and the designated-review slot has no such line unless you write one — and treat a recurrence as a one-line sighting, never a finding — a fresh reviewer cannot know a question was answered last week, and a phase whose closed questions keep reappearing can be structurally unable to reach two clean passes. A red-team claim **you verified as false from source** is refuted, not deferred: record the refutation with its evidence **and hand it forward with the closed questions into every later reviewer's brief** — a refutation only the record holds re-arrives as a fresh finding. Style nitpicks you decline, with a stated reason, don't reset the counter either. Choosing to *take* any of these as a fix is still a diff change, and whether it resets is the next rule. **A repair resets the counter to zero when it changes what shipping code does, or a claim about what it does**; a repair that does neither — wording, a comment deleted from a code file, a test, a gate instrument, a steering document — does not, and the pass that follows certifies the deliverable as it now stands, consecutive with the clean pass before it. **You judge that from the diff, never from a seat's label or your own**: list the files it touched and read its content for a behaviour claim, because "prose-only" is a description someone gives a change and not a property of it, and a repair that reworded a docstring into a different claim about the lock has changed behaviour text whatever it was called. Where it resets, the phase needs two fresh clean passes over the deliverable as it now stands: re-running the gate once and calling that pass two exits the phase on a single clean pass of the work you are actually shipping. Where it does not, the delivery line (step 7) names both revisions and what changed between them. **The pass that follows a repair is pointed at the repair**, by name and by isolated diff, as its first target — not only that the fix works, but whether it broke a neighbour, restated something inconsistently, or made a claim that was merely loose into one that is false — **and then at the whole artifact**, which the brief says in those words and the seat confirms it swept: a seat told only "the repair first" anchors there, and one prose run went eight rounds with no seat re-reading the rest of the report. Say so in each seat's brief, and hand the seats the repair's own diff alongside the full one. **A repair writes no claims about itself.** No count, coverage statement, round number, gate history or "verified by" note goes into a comment, a docstring, a spec or a commit message in the course of a repair, with one exception: a claim the reader needs, proved by breaking the code and watching the check fail. Half of all blocking findings across three live repos landed inside the previous round's repair, prose the repair wrote was the largest single class, and a claim a repair makes about its own thoroughness is stale by the next round. Before the next pass opens, run the class question below over the repair's own diff for the same mark. **Documentation the work needs is written after the phase exits, or after the user ends the rounds, never mid-round**: a docstring, a README section or a guide written against a revision still under repair is rewritten every round and reviewed every round, and none of that certifies anything. Record each documentation obligation on a documentation list as it arises — a section of the deferred list is fine — and write the list once the certifying passes are in. Two things are not that deferral: a false claim the gate found is a defect and is repaired in the round like any other, and where prose *is* the deliverable, the deliverable is not documentation. The docs written after exit take the docs-only native check from step 3, run by you and by no seat: every item on the list written, every edited claim re-verified against the source it describes, a link and path check; a failure is fixed where it sits and the check re-run, and it never reopens the phase, because the code did not move. A repair is written under time pressure, against a finding rather than against the whole artifact, and by the one party who cannot review it, so it is the least examined text in the deliverable at the moment the next pass opens. In a driven 13-round run on a prose-heavy deliverable, eight rounds found their worst blocking finding inside the previous round's fix, including two that turned a correct-but-loose sentence into a false one and one that repaired a rule in a file the consuming agent never loads. This is not the class question, which asks where else the *original* defect's mark appears; it asks where the *fix* reached. **The valve counts unresolved rounds: +1 for each gate pass that produces a blocking finding, and it never resets.** It is deliberately a different counter from the exit count above — a valve that resets whenever work happens never fires, and one that counts every pass trips on a phase that is merely thorough. At each multiple of 4 — 4, then 8, then 12 — stop and escalate to the user instead of grinding; if they say continue, the valve **re-arms at the next multiple** rather than being spent, and it does not fire every round thereafter. **Only a ruling given after the firing re-arms it**: a standing instruction to continue, or not to ask, authorizes rounds, never valve passes — the firing exists to put a diagnosis in front of the user that no earlier instruction could have weighed. This is a loop-health stop, not a decision escalation. **Keep both counters on disk, not in context**: each round, write the phase, the round number, and every counter's current value to a durable record — the wrapper's own artifact where it has one, else a run-state file beside the work or in the scratchpad, named in the report. A compaction zeroes an in-context counter and announces the loss to nobody: the exit gate silently restarts at zero and the valve never fires at all. **Where the run sits inside herdr (`HERDR_ENV` is `1`), the same per-round write also publishes the counters to the sidebar**: run `node <plugin-root>/hooks/dctr-token.mjs <round> <exit-count> <valve>` — the script lives two directories above this skill's own base directory — and it is display only, never the record: outside herdr it stands down with a reason and exits 0, and any failure of the command itself — script missing, node absent, herdr refusing — is noted in one line and ignored, never blocking, resetting, or failing the round, because the durable record is the counter and the token is only its shadow. That is the whole of its fallback. **On resume the durable record is authoritative** — phase state, counters, open waves, findings — and a value you believe wrong is corrected by a `supersedes:` entry, never by reinitializing: a counter rebuilt from memory erases the unresolved history the valve fires on. **That record has two parts, and the second is handed to no reviewer**: whatever the wrapper's artifact carries for agents to read, and a trailing section — headed `## Run state — orchestrator only` where the wrapper does not already name it — holding the counters, the round history, the per-finding lines below, **any seat that ran substituted, with the rounds it covered** — a compaction otherwise leaves a fresh agent reading clean rounds with no way to know they were degraded — **the retries each seat has spent this phase**, and **whether step 6's once-per-phase simplification has run**, since a resuming session that cannot tell either runs it twice or skips it, and both are silent. Where that artifact is handed to a reviewer by path (as `matts-code-review` reads its spec), or is the deliverable itself, the second part goes in a separate file instead, `<first-part>-run-state.md` beside the first part, so that the next session finds it by convention. **Putting it beside the first part is what then puts it in front of the reviewer, so two things have to be made true and neither is automatic.** Keep it out of the tree a reviewer reads: ignore it where the project is under version control, and exclude it by path from any diff you hand an agent, because a reviewer pointed at a diff reads what was committed and the file is beside the work. And keep it out of the reviewer's own search: `matts-code-review` hunts a spec under `docs/`, `specs/` and `.scratch/` by feature name, which is where the first part usually sits and what this file is named after, so hand it the spec path rather than letting that search run. A reviewer told this is the second clean pass, or that the valve fires next round, has been told how badly the pass needs to be clean, which is the one thing a reviewer must not hold; handing a fresh critic its predecessor's own returned text on one piece of work is not that. Wrapper-level outer loops (like audit's loop-until-dry) sit outside this per-phase gate; a new outer-loop finding starts a new phase, it does not reopen closed ones. **A wrapper may replace this exit condition and its counters, but only by stating the replacement explicitly** — `doctrine-gauntlet`'s pure-gauntlet mode overrides the four-loop valve in exactly that way, and says so. A wrapper silent on the subject inherits this gate as written, and nothing else in the posture is a wrapper's to override. **One replacement is defined here, for any wrapper whose deliverable is prose to adopt by name: the prose-deliverable exit.** A report, a spec, an ADR or a written document is production-facing in every sentence, so the narrowing above exempts nothing in it, and three adversarial seats over several hundred lines return a blocking finding every round however good it gets; in the recorded runs no such phase ever closed on two consecutive clean passes, and every one ended by the owner ruling the same shape. That shape is the exit: **after the first clean full pass, or at the valve's first firing where no pass has come clean, run one closing round scoped to the diff since the last fully reviewed revision, then exit.** Where nothing changed since the clean pass, the closing round has nothing to review and the phase exits on that pass. It is a closing round and not a certifying pass: the two names are kept apart because one is a diff-scoped review that ends a prose phase and the other is one of the two full passes that certify a shipping revision. The firing still puts its diagnosis to the user, but under this exit you do not wait for a ruling to open the closing round — the ruling this exit replaces is the one the owner gave at every such firing — and a user who wants otherwise says stop. A firing under this exit is therefore answered, not open — "a valve fired and unanswered" below does not describe it — and the record names the closing round as what the firing produced. A finding inside that diff is repaired; a false production claim found there is deleted or marked at the claim site with a pointer to its punch-list entry, never left standing as written; a finding outside the diff is a one-line sighting for the punch list, never a blocking finding; and the phase ends *Exited* under this replacement with the punch list named in the record and in the delivery line. No further full passes. The valve and the exit count run unchanged up to the trigger.

**A phase ends in one of five states, and the record names which.** *Exited*: the phase's exit condition was met — this gate's two consecutive clean passes, or the replacement a wrapper states in its place. A wrapper's replacement may exit carrying a punch list of findings it did not fix; the record names every one and the delivery line carries the list, so an exit of that kind is never read as no known defect. *Stopped*: the user ended the loop — record the round, every counter, and every finding still open at that moment as open, never as clean. *Shipped at an escalation*: the user chose to deliver from the valve's stop or from a wrapper's replacement for it — the same record, plus what the last round found. *Blocked*: the session ends with a direction question (step 1) unanswered — say which. *Unable*: execution ended and cannot resume by itself — a reviewer seat that failed both retries with nothing to substitute, credentials or infrastructure gone, write permission lost, a wrapper's own lenses exhausted (audit's "say so and stop"), a mandatory gate that cannot run and that no wrapper lets you waive — record what ended it and what would restart it, or that you do not know and what would find out, because this is the one state where "resume" is false and the next session must not try. Nothing else is Blocked or Unable: a gate you cannot run but may record as unrun is an unrun line (step 3), where the wrapper says so it is a blocking finding awaiting a ruling, and a phase with a ruling in flight has not ended at all. **A phase that has not ended is *Open*, and the record names that too**: a valve fired and unanswered, a ruling in flight, a wave still out, a session that stopped mid-round. *Open* is not a fifth ending, it is the absence of one — the counters stand, nothing is clean, and the next session resumes rather than reports. Write it every time you write the record while the phase is live, so that a record carrying no state at all means the write was lost and never that the phase was fine. **Where the record carries more than one state line, the last one in the record is the current one**, corrected the same way any other line is: a record long enough to have a header will disagree with itself, and the reader needs the rule rather than a judgement. **The record also names every wave the moment it goes out** — under the round that dispatched it: which seat, what it was handed, and the handle that finds it again (a task id, a run id, a thread), or that there is none, in which case a return never found is a failed seat — with one guard: a mutating wave you cannot find is unreachable, not known dead, so its replacement never goes into the same worktree, output directory or port (step 2); it gets its own, and the original's are treated as still in use — and its return is appended under whichever round is open when it lands, attributed to the round that sent it, because the record is append-only and a round already written is never reopened. Three cases follow and none needs a rule of its own. A wave still out when a session resumes shows as dispatched with no return, so the resumed session checks the job's terminal status before doing anything else. A wave whose job failed is re-dispatched once for a builder or finder seat — and if that fails too, the work comes back to you, in-line or split smaller, with the seat's failure recorded; a failed builder is never a reason a phase is *Unable* — and for a reviewer seat follows the retry-then-substitute law under Fallbacks; where the wrapper runs its own regime for that seat (the gauntlet's builder and critic retries), the wrapper's governs. And a wave that returns late, even after the phase's state was written, is a finding against the artifact **as it stands now**, not a correction to history: its findings go under the current round, a blocking one makes *this* round not clean — the exit count resets now, the valve counts now and fires now if that reaches a multiple — and the state line is superseded back to *Open*, which where the artifact already shipped means step 7 runs again on the fix. No earlier round is recomputed. Replaying history is exactly what an append-only record exists to prevent, and the artifact is either defective now or it is not. Only the first is clean. The other four are outcomes, reported as such at step 7 and written into the second part of the durable record this step already names, since that is what the next session resumes from: a record that says "no known defect" where it should say "stopped at round 6 with the gate open" has converted an instruction into a pass, and the next session inherits a certification nobody earned. (*Stopped* is a phase state; "ruled closed", above, is a finding state. Never write one for the other.)

**Every blocking finding from a gate pass that survives verification gets one question, and its answer goes on disk: where else would whatever produced this have left the same mark?** Ask it of all of them, not only the ones you suspect your own earlier rounds caused. **Do not label the cause**, tempting as it is — that a doc went stale *after* round 3 changed the code does not show that round 3 did it, the finding may have pre-dated the phase and only become visible, or have several causes, or be partly each; you would be recording a guess, and the diagnosis below would then count it as a fact. The class question needs none of that. It asks about shape, not history, and a shape either recurs elsewhere or does not, which is a thing you can go and look at.

**Fix the class, not the instance**: clear every site the question turns up that you may touch, in one round, because a round that clears the instance has scheduled the next finding and reset the counter to go and find it.

**The question sweeps wider than the deliverable; the fix does not.** Look everywhere the mark could be, the phase's boundary included — a boundary limits what you may change, never what you may look at, and a sweep stopped at the edge reports a class cleared when only the visible half was. **How wide the looking itself may go is step 1's bound, and it governs here unchanged.** Then split what it found. Sites inside the boundary are cleared this round. Sites outside it are written down and handed over: on the deferred list you carry to step 7, with their locations and what the mark is, and in the record. Never silently fix an out-of-boundary site and never silently drop one — the fix is a scope violation its owner did not ask for and no gate here will catch, and the silence leaves a known defect where the only party who could act on it never hears. **Split them on what the site does against the deliverable as it stands, never on what caused it** — the same test everything else here blocks on, and the class question above already refuses to label a cause for reasons that apply here unchanged. Go and look. Where the site still works against the deliverable as it now stands, it carries the mark and nothing more: it does not block the phase and does not reset the counter, and you hand it over. **Where the deliverable as it stands leaves it broken, it blocks like any other defect**, and you need to know neither why nor whose fault it is — an in-boundary change to something shared, read or called from outside the boundary leaves the deliverable wrong as it stands, being forbidden to edit the casualty is not permission to ship the break, and a site that was already half broken is still broken now. It stays blocking until the user widens the boundary, accepts the break, or the in-boundary change is made compatible, which is usually the fix that was available all along. Where the boundary itself is unclear, or where looking cannot settle it — you can find the site but cannot build, run or query it — the sites go on the list and the question goes to the user, left unresolved rather than guessed into either branch: an ownership question is not resolved by editing, and a compatibility question you could not answer is not resolved by assuming the answer you would prefer.

**The answer goes in the orchestrator-only section of the durable record, under that round's entry, one line per blocking finding**: the finding, the artifact it landed in, where else you looked for the same mark and what you found, and — once acted on — what cleared it (the fix, the ruling, the re-run), else "open", and whether a check was built for its class, or why not. **Later rounds add to the record; they never edit it.** A round that clears a finding writes a new entry under its own round — `clears:` and the finding quoted as its line states it, with the round that line was written under — and a round that finds an earlier line was wrong writes `supersedes:`, the quoted line and its round, and the correction; the earlier line stays exactly as written. Round plus quote is the reference: it survives a resume, needs no allocator, and two identical findings in different rounds stay distinct. A wrapper that numbers its own list (audit's confirmed list, research's gap ledger) keeps doing so for its own purposes; this record still quotes. That keeps the record append-only, which is what a wrapper's "append a block each round" already assumes and what a resume after compaction needs, and it keeps the correction visible to whoever reads next instead of silently rewriting an earlier round into having been right. **"Cleared" is a claim about the deliverable, so it carries evidence of the same kind the finding did**: for a gate, the check's exit status and output; for a reviewer's finding, the artifact line or render that now satisfies it, or where the fix was a deletion, the diff hunk and the search that now finds nothing; for a re-run, the reviewer's returned text; for a ruling, the user's words, or the documented scope that puts the finding outside the deliverable. Cleared-without-evidence is not cleared: leave it open. This is not ceremony — a line recording a fix that did not work reads exactly like one recording a fix that did, and the diagnosis below counts them the same. A wrapper's own list of what that section holds may omit these lines; write them anyway. The diagnosis below is built from these lines and the per-round entries beside them, and a compaction takes both if they lived only in context. **A phase that runs no gate produces no findings and so no lines at all** — `doctrine-debug`'s diagnosis phase is the case — and there the per-round entries are the whole of it. And **when a class of finding can be caught mechanically — a grep, a schema, a script that reads one artifact against another — build the check before running another round.** It then joins the phase's native checks for every round that follows, and it is written down where the project documents its gates so that step 3 finds it next time — or, where nothing documents them, where you may not write there (step 7), or where the wrapper forbids code changes, beside the run-state record and on the deferred list you hand over, so it is named rather than lost. A review round costs a wave of agents and finds one instance; the check costs seconds, finds the class, and runs inside the round before the diff leaves your hands. That is the difference between a loop that converges and one whose length is set by how many artifacts the work touched. The code in a project usually has this already — tests, a typecheck, a linter — and its prose, its config, its fixtures and its generated output usually do not, which is why findings pile up there.

**The valve's escalation is a diagnosis, not a bare yes/no.** The stop still asks the user to continue or to ship; the diagnosis is what it asks with. **It has two halves, and the first is the one the decision turns on.** A user choosing between continuing and shipping is asking what shipping *means*, and loop statistics do not answer that.

**What shipping now would mean.** One line first: known defective or not, and how many blockers are open. Then every blocking finding still open, each stated as its consequence rather than its title — what it breaks for a user or a caller, or, where nothing functional breaks, the clause of documented law it fails and what that costs at acceptance or delivery — "fails markdownlint" is a title, "heading levels skip from h1 to h3, and the docs build the release gate runs rejects it" is a consequence — and how many are exposed, or that you do not know. Every gate that is unrun and why (step 3). Whether the artifact as it stands is known defective — at a firing it usually is, since the pass that fired the valve produced a blocking finding, and a diagnosis that never says so has buried the one fact that decides the question. Then what continuing would cost: the next thing you would do, and what it would take.

**Why the loop has not closed**, over the rounds since the last firing, or since the phase opened at the first: which artifacts the blocking findings landed in; for each, whether the class question found other sites and whether a mechanical check now covers them, and where it does not, why one was not built — a class that keeps turning up new sites round after round is the loop telling you where it is going next; and what the fixes since then changed. Four rounds of findings in one artifact from one cause is not a phase that needs more rounds, it is an artifact with no gate.

**And whether the exit condition is reachable at all**, which is a different question from whether the work is nearly done and the only one a firing can be too late to ask. A gate correct work cannot satisfy is broken, and this posture applies that test to a project's gates without ever applying it to its own. The shape to watch for: the deliverable is mostly prose, every seat is adversarial, and a false claim is blocking by definition, so three fresh critics over several hundred lines of it return a blocking finding every round no matter how good the artifact gets. A driven run reached round 13 that way, never once clean, while the findings fell from state-loss defects to comment accuracy without the counter ever moving. Say which it is: rounds are still buying defects a user could hit, or the gate has stopped discriminating and is now scoring the reviewers' thoroughness. Where it is the second, **the escalation may propose a narrowed blocking definition for the user to rule on** rather than only continue-or-ship, since the exit condition is already a thing a wrapper may replace by stating the replacement explicitly, and a firing is where the orchestrator has the evidence a wrapper author never had. Propose it as the wrapper would: the narrowed definition in one sentence, what it stops counting, and the rounds' findings re-scored under it so the user sees what the change would have exited on. The user rules; you do not narrow a gate you are being measured by. Record the ruling where later reviewers read it, because a seat that does not know the definition changed will keep filing against the old one.

**Reconcile every line — open and cleared alike — against the artifact at each round's clean determination, and once more before you build any of this.** Reading only the open ones cannot catch a false clearance, and a stale open keeps passes unclean without ever advancing the valve, so a reconciliation that waits for the valve may never run. This is the moment the record stops being bookkeeping and becomes the thing a person decides on. A line that says open and was fixed three rounds ago, or says cleared and was not, is corrected by a `supersedes` entry and that is the whole of the bookkeeping. **The counters follow what the artifact shows, exactly as they would have had the line been right all along**: a false clearance means that finding is outstanding, so the round is not clean and the exit count resets; a stale open means nothing was outstanding, so nothing moves. The discrepancy itself is not a finding against the deliverable and never enters the diagnosis as one. A user asked "continue?" on a bare count has been told nothing they could rule on; one handed counts computed from lines nobody checked has been told something worse. A wrapper that replaces the valve with a counter of its own (`doctrine-debug`'s hypothesis waves) fires the same shape in its own units — what each counted round produced, what repeated, and what nothing cheaper than another round could have seen — and so writes what each counted round produced into the orchestrator-only section as it goes, beside the count, or the diagnosis exists only in context. Write the third at the time too, per round: **what non-round instrument could have answered this**, or that none could. It is a judgement about the round you have just run, and answering it afterwards from memory is the thing this record exists to stop.

**6. Simplify early and often.** Run a simplification review **once per phase, before the consecutive clean passes that certify the shipping revision** (/ponytail-review if installed, otherwise /simplify or a YAGNI pass: delete over-engineering, dead branches, speculative abstractions). Its diff enters the gate per step 5 and is part of what the exit passes certify; you do **not** run it again after them — a simplification landed after a clean pass changes what shipping code does and so resets the count the phase just earned, which is why it runs before the certifying passes begin, and only once. Reuse existing modules, code patterns, and UI tokens. Don't reinvent the wheel; don't build what won't be used.

**7. Deliver.** A task ends with the project's delivery norm (commit, PR per the repo's CLAUDE.md), never with "the loop is clean." **Push only where that norm says to, or where the user has said to** — some repos' convention is explicitly the opposite, and where nothing documents a norm there is nothing to defer to: commit locally and ask before you push or open a PR. **Where you cannot write where the work must land** — no permission, or the user said read-only — build in the scratchpad (the session temp directory if there is one, else a temp directory outside every repo, named in the report) and hand over the diff, the artifacts and the deferred list together. Never inside a repo you were told not to write to: read-only means the working tree too, not just the commit. Work is not done until it lands. **Whatever triggers delivery, one line goes first: whether the shipping revision carries two confirming clean passes, and which blocking findings are still open** — and, where the two passes span a repair that did not reset (step 5), both revisions and what changed between them; where a wrapper's replacement exit shipped a punch list, the list. A user directing delivery is owed that line before it lands, and it changes which state the record names, never what the states mean (step 5: a user-ended loop is *Stopped*, delivery from a valve stop *Shipped at an escalation*). Close by walking the original request item by item and naming where each one landed, or that it was deferred and why. When a brief of N items ships N-1, every piece of work that ran still passed its gate, so the gap never surfaces as a failure — absence of work is invisible to checks that only inspect work.

## Fallbacks

When a referenced skill isn't installed, degrade gracefully instead of stalling. **Two rules govern every substitution below, and step 3's law about unrun checks is the model for both: a check you could not run and a check that passed are indistinguishable in a report that mentions neither, and so are a reviewer you could not reach and a reviewer that cleared you.**

**Substitute for an absence, retry a failure — but bound the retry.** This table is written for a tool that is not installed. **A seat that reports its own tool as not installed or not found — in its return, or in the job record step 4 has you retrieve — is treated as absent for the rest of the phase, exactly as a tool that failed both retries is, whatever the plugin manifest says.** The common shape is a wrapper plugin present with its backing CLI unreachable, `codex:codex-rescue` answering that the Codex CLI is not installed. Substitute now, from that plugin's own row in the table read as if the plugin were missing, spend no retry, and record the seat's words as the reason. This makes no judgement about whether the tool is durably gone, which the rule below forbids and which you cannot make: a binary really absent and a session whose PATH was captured before it was installed produce the same words. The ground is the class of the return, not its durability: the retry budget below exists for failures a later minute can cure — capacity, a timeout, a crash — and a tool reported as not installed is cured by an install or a restart, never by a minute, so retrying it spends a bounded seat to learn what the return already said. A session that resumes the phase re-dispatches the seat once before substituting again, since the environment it resolves the tool in may have changed. Two driven runs and one live session each burned a retry on this before the branch existed. A tool that is installed and *failed* — a capacity error, a timeout, a crashed process, an empty return — may only have failed for a minute, and substituting on the first failure converts a bad minute into a bad run: a reviewer unavailable at round 2 is often back by round 5. **Do not try to tell a transient failure from a durable one**, since a revoked credential and a busy server return the same nothing. Retry it once now and once more in a later round; if both retries fail, treat it as absent for the rest of the phase, record that, and substitute. Two retries after the original attempt, then a decision — nothing here is a licence to retry until it works, and no counter is watching this loop. **The count belongs to the seat, and step 5's record holds it, so it survives a resume**: a seat that spent one retry last session has one left, not two. It is scoped to the phase, like the absence it governs. **A dispatched agent that returns nothing, or returns only progress output, has not reviewed anything**: check the job's terminal status, never just that the agent came back, because a dead reviewer prints what a clean one prints. **A seat that never returns is the same failure**: give every asynchronous seat a deadline at dispatch — **derived from what that seat is known to take**, where anything documents it; where nothing does, because it is that seat's first dispatch, set it long rather than short and write the figure down as the guess it is. A deadline shorter than the seat's known typical run makes the kill evidence of nothing — check liveness against the handle the record holds for it, and kill a seat past its deadline with no new output in its own artifact — that is one of the two retries spent. Terminal status and liveness come from the job's own record — an exit code, an output file that grows — never from matching process names, which finds your own watcher and calls it the job.

**Record the substitution, and let it qualify the exit.** Write down which seat was substituted, for which rounds, and why. **A substituted pass still counts toward the two and the phase may still reach *Exited*** — the alternative is that one missing optional tool blocks every phase forever, which is what "degrade gracefully instead of stalling" exists to prevent. What changes is not the arithmetic but the claim: an exit reached with a substitute in a seat says so, naming the seat and the rounds, because two clean passes of the full gate and two clean passes of a degraded one are different statements and only one of them is what the wrapper named. The sharpest case is the red team, because the substitute for a cross-model adversary is a **same-model** one, and a reviewer built like you has blind spots correlated with yours. It is not blind in the same places, and it does real work — the fallback is a fresh context prompted to refute, which is why it is the fallback and not nothing. But the overlap is invisible from inside, because the substitute returns confident, well-formed, correctly-shaped findings whether or not the class you both cannot see is in front of it. Say so in the report rather than letting a fallback be read as the thing it stood in for.

## Red flags

- A phase advanced on one clean pass where no wrapper states a replacement: the gate is two.
- A seat's finding on wording that changes neither what the code does nor what it is for, filed as non-blocking and carried on the deferred list.
- A repair that wrote a count, a coverage claim or a round number into a comment, a docstring or a commit message.
- A README section or a docstring written mid-round that no finding demanded.
- A repair called "prose-only" by the seat that wrote it, and the count left standing on that word.
- Red-team finding acted on without reading the source it cites.
- New helper/module written when an existing one grepped up in 30 seconds.
- Questions saved for the end instead of asked before wave 1.
- Two parallel agents mutating the same files without isolation.
- A multi-item brief closed without checking each item actually shipped.
- A gate trusted without asking what it measures.
- Native checks read as "typecheck and tests" in a project whose real gates are a linter, a schema check, or a content law.
- An unrun check reported as a clean one.
- A finding re-filed by the next pass and waved through as not new.
- A repair to shipping code landed, the gate re-run once, and that counted as the second clean pass.
- Counters kept only in the conversation, where a compaction takes them and says nothing.
- Two agents with disjoint files sharing one build directory, dev server, or port.
- A red team dispatched with "refute this" and no artifact, no axes, and no bar.
- Pushed because the posture said push, with no repo norm and no instruction saying so.
- A phase the user stopped, recorded as clean, as "no known defect", or as "ruled closed".
- The same artifact taking every blocking finding round after round, each fixed one instance at a time, and nobody asking where else the same mark would be.
- A valve escalation that reported a round count and nothing about where the findings landed or why.
- A dispatched prompt still carrying an unresolved template marker, or an empty slot where the artifact should be.
