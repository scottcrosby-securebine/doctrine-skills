# Doctrine Orchestrate

Several doctrine phases of one epic, run at once and landed one at a time.

**REQUIRED BACKGROUND:** Read the `doctrine` skill first: it defines phases, seats, the record, the gate (step 5), alarms and their diagnosis, auto-cycle and the fallbacks. Read `doctrine-project` too, since every run here sits in a repo it tracks, and its `formats.md` for the project file, the epic record, the Members line's ordering clause and the ruling Kinds. This file supplies the task shape and restates neither. Paths below are relative to the plugin root unless they start `<run>`, `<repo>` or `<checkout>`.

The core discipline is relay. You, the orchestrator, write no code and run no phase's work. Each lane is its own doctrine phase under its own wrapper, with that wrapper's designated review and red team. The gate this shape adds is the merged-revision gate the merge session runs for each lane, and the epic's own exit stays as `doctrine-project` gives it. Your record is the record of your own phase, under the project file's `Records:` path, and it carries your `relay:` lines and every line doctrine step 5 puts in its orchestrator-only part.

## Hosts and refusals

Run every check here before anything else, and stop at the first that fails, saying which and why:

1. **Claude Code only.** On Codex, refuse and say that Codex parity for an orchestrated run is a later epic.
2. **herdr.** Every session of a run lives in its own herdr pane, so without herdr (no `HERDR_ENV=1`), or in a contained session (`DCTR_VIEW_REQUEST_DIR` set), refuse to start a run and say that the run's sessions, sender and watcher all need herdr panes.
3. **A project file.** Refuse in a repo that carries no `docs/PROJECT.md`, and say so. Judge that by the file itself, never by whether `runRoot` returns a run, since with `DCTR_RUN` set it returns one in any repo.
4. **Your role.** Refuse in a session whose `DCTR_ROLE` is not `orchestrator`, write the command that starts one to a new file of its own that no file of a run shares, one `mktemp` creates, and print the launch line that runs it, `sh '<that file>'`, which carries no PATH and so fits herdr's 1,024-byte limit on a typed line whatever this session's PATH is. Name the model in that command by the id this session runs on, since `<run>/model/orchestrator` is not written until the run starts: `cd '<checkout>' && env DCTR_ROLE=orchestrator DCTR_CALLER=orchestrator DCTR_RUN='<run>' CLAUDE_CONFIG_DIR='<config dir>' TMPDIR='<tmp>' claude --model '<model id>'`, with this session's PATH added as one more assignment, `PATH=` and its quoted value, before `TMPDIR`, this session's config dir and TMPDIR, and `<run>` the absolute path of `<Records>/orchestrate/`, `<Records>` being the project file's `Records:` path. In every command this file prints, a quoted value goes in single quotes with each `'` in it written as `'\''`, so the shell expands nothing in it, a `<text>` above all. A session with no `DCTR_ROLE`, such as a second session opened by hand in your checkout, is not in the run.

## Roles and the run

A run has three kinds of session, each a Claude Code session in its own herdr pane: you; one lane session per phase; and the merge session. The lane watcher and the sender are scripts, not sessions, and the owner answers questions. A lane is not a seat (doctrine step 5): you never wait on one, and you cycle on your own schedule.

Every session reads its role and its run from its own environment, set by its launch line, so a `/clear`, a restart or a seat keeps them. `<run>` holds `inbox/`, `held/<role>/`, `pending/<role>/`, `launch/<role>.sh`, `model/<role>`, `waiting-questions.md`, `limits.log`, `events.log`, `guard.log`, `lane.log`, `tmpdir` and `wake-all.lock`. `node hooks/dctr-project.mjs board` writes `board.md`, one row per lane phase, into the Records path, and is how you read the run at a glance.

The only text any session or script types into a run session's pane is one of four fixed lines: `/clear`, `RESUME_LINE` from `hooks/dctr-lib.mjs`, the nudge "Read your brief and your held folder, then act on them.", and a role's launch line as `lane.log` records it. Everything else is message text and goes through the sender.

## Run start

In this order:

1. Your checkout holds a branch of its own, never the integration branch.
2. **Ignored state.** You never edit `.gitignore`, so check before the run starts that every repo of the run, your checkout and the code repo alike, whether public or private, already ignores the state its sessions write there: run `git check-ignore SESSION_MEMORY.md docs/handoffs/ '<Records>/'` in each. Where it does not print all three paths, stop the run and tell the owner which path in which repo is not ignored, to be added to that repo's `.gitignore`.
3. **One question to the owner**, in one message: the full model id, the tier and the cycle cap for each role (yourself, the merge session and every lane), and your own time budget. Write the time budget into your anchor (doctrine step 1).
4. **Capacity.** Run `node hooks/dctr-orchestrate.mjs capacity <tier> '<transcript path>'` once, at your own tier and on your own transcript. On `refuse`, put the line to the owner as your next question, and take no further step here until a run of the command on your transcript prints `accept`. Run it for no other role: each role runs it on its own transcript as the first step of its first turn, as its brief says (Lanes). Decide capacity by that command alone: compute no window, load or margin yourself.
5. Write each role's model id to `<run>/model/<role>` before that role starts, since its launch line reads the file.
6. Write the tier and cycle cap of each lane, and of the merge session, into that session's first handoff, from which it writes its own `auto-cycle: on` line. Never write a lane's or the merge session's auto-cycle line into its record yourself.
7. Start the lane watcher with `node hooks/dctr-lanewatch.mjs start`.
8. **The merge session, before any lane**: `node hooks/dctr-lane.mjs create merge '<repo>' <integration branch> '<handoff>'`. When `create merge` refuses, stop the run and say why. Create no lane after that refusal.
9. **The guard probe.** Attempt one Write to `<checkout>/guard-probe.txt`, which is outside every path the guard allows you. Then read `<run>/guard.log`. When it has gained no line `<ISO time> Write <checkout>/guard-probe.txt` (the absolute path), stop the run and say the guard is not on. Judge by that line, never by the Write's error alone, since a guard failing open gives an error from nothing and no line.
10. Create each lane with `node hooks/dctr-lane.mjs create <role> '<repo>' <base> '<handoff>'`, its first handoff written under your own `docs/handoffs/`.
11. Once the last lane's `create` is done, run `node hooks/dctr-project.mjs board`.
12. Then run `doctrine-handoff` for your own phase, so your kickoff chain exists from run start and your own auto-cycle hooks do not stand down, and carry on with the run.

## Lanes

- **Each lane is its own doctrine phase**, never a sub-record of yours: its own `- phase` line under the epic's `## Members`, its own Coverage line on the items it serves, its own record and its own wrapper and gate.
- **Overlapping lanes run in separate worktrees with disjoint files**, each with its own record and its own auto-cycle line.
- **Every worktree transition is `dctr-lane.mjs`'s**: `create`, `reset`, `archive` and `remove`, for every lane and for the merge worktree, never a `git worktree` or `git reset` by hand, and no lane makes one. The one exception is the merge session's rollback under Merges and ordering: resetting the integration branch, inside the merge worktree, to the commit before a merge whose merged-revision gate did not pass is that session's own step and not a worktree transition. `archive` before `remove`, and never `remove` a lane whose session still runs.
- **A lane knows it is a lane from its first handoff**, whose first action is its brief. The brief you write for each lane, and for the merge session, says:
  - As the first step of your first turn, before any other work, run `node hooks/dctr-orchestrate.mjs capacity <tier> "$(node -p 'JSON.parse(require("fs").readFileSync(process.argv[1], "utf8")).transcript_path' "$TMPDIR/dctr-autocycle/pane-$(printf %s "$HERDR_PANE_ID" | tr -c 'A-Za-z0-9_-' _).restored")"`, with `<tier>` the tier this handoff gives you. The inner command prints your own transcript's path from your pane's restore file. When the command prints `accept`, go on with your brief. On any other output, send that output as a `question` report and do nothing else.
  - Read your held folder at each resume, before each commit and after each report you send, and act on what is there.
  - Your phase stays open for the whole run. Record your exit's result as your wrapper says, but write no state line other than Open until a held message from the orchestrator says the run has ended, and then write the state your exit gives.
  - Send every question for the owner to the orchestrator as a `question` report (`node hooks/dctr-send.mjs report question '<text>'`), never to the owner directly, with each `'` in `<text>` written as `'\''`.
  - Ask the orchestrator for each lifecycle write by a `request` report, and take no step that needs it until the answer is in your held folder (`doctrine-project`, its orchestrated-run rule).
  - Send each report as `node hooks/dctr-send.mjs report report '<text>'`, with each `'` in `<text>` written as `'\''`, and make no worktree transition.

## Messages and the wake

- **`hooks/dctr-send.mjs` is the only way a message reaches a session of the run**, the merge session included (`held/merge/`). `send <role> '<text>'` writes the text to the role's held folder and types at most the nudge. A sender never types free-form text into a lane: every message goes to the lane's held folder, and the lane reads it after its next resume.
- **A paused lane is woken only by `dctr-send.mjs`**, its `wake <role>` or its `wake-all <run>` subcommand, never by lines typed by hand.
- **Relay lines.** The sender writes the `relay:` line for each send or wake you make. You write one `relay:` line yourself for each report you relay to the owner.
- **Your wake is a Monitor on `<run>/events.log`**, the lane watcher's events log, read through a cursor. The Monitor only wakes you: a notification's text is never the list of events, which you read only from `events.log`. Your cursor is the number on the last `- events-cursor: <n>` line of your record. Your first session writes `- events-cursor: 0` there at its first arm, and after each resume you read the cursor from your record before your first read and arm. At the start of every turn, and again before you end a turn in which a notification arrived after that turn's last read, read `events.log` from the line after your cursor, act once on each line, and append `- events-cursor: <n>` naming the last line you read. Arm each Monitor on `tail -n +<cursor + 1> -F '<run>/events.log'` after a `touch` of that file, with a timeout, and re-arm it at once each time it expires. An armed Monitor holds your Stop, so stop it as the last step before your ready line. After your resume, your first steps, following your handoff's first action, its read of `<run>/events.log`, are to read your cursor and then re-arm the Monitor. Copy this rule word for word into every handoff you write for your own phase: it is the one exception to `doctrine-handoff`'s "Reference, never duplicate", since a paraphrase of it once lost the cursor.
- **On a `held <role>` event**, which the watcher raises once the role's pane reads ready while a message `send` held without a nudge is still unread, nudge the role again with `node hooks/dctr-send.mjs wake <role>`.

## Questions and alarms

- **A waiting question lives in `<run>/waiting-questions.md`**, the one source for it, and never as a `question:` line in your record, which would pause your cycle. At each context warning copy every unanswered question as `doctrine-backup`'s and `doctrine-handoff`'s orchestrator profiles say.
- **One question to the owner at a time.**
- **At an alarm, yours or a lane's**, write doctrine step 5's diagnosis with a recommended option and the options beside it, for the owner to answer in one word. Never rule on an alarm yourself.
- **A per-model usage limit** is a `model` line in `<run>/limits.log`, and the watcher's `limit <role> model` event names it: the `/model` switch answers it. Put that switch for that role's running session to the owner as one question naming the role and the model id you recommend. The role's current tier is the tier on the last `auto-cycle: on` line in the role's record, or, while the role has written none, the tier from the owner's answer at Run start's step 3, and its current cap is the cap on that line or from that answer. Recommend a model with no capacity verdict, since the role checks capacity itself once it runs that model. Record his answer as a `note` ruling in the epic record whose quote holds his own words (`formats.md`, Entries), never as a `ruling:` line in a session's record, since any later `ruling:` line clears a fired alarm there (`pausingStates` in `hooks/dctr-lib.mjs`). His answer is the ruling, and the switch goes in this order. First write the model id he chose to `<run>/model/<role>`, so a later restart starts that role on it. Then the owner types `/model` in that role's pane himself, waiting for no report: no session, seat or script of the run types it, since only the fixed lines are ever typed there. Then, once the owner says he has typed `/model`, send the role a message with `dctr-send.mjs send`, and decide what follows from the lines the sender prints, never from its exit code (E15 Messages): (1) no `dctr-send: held <file>` line means delivery is unknown, never that the message was not delivered, so never send it again: look in `<run>/held/<role>/` for a file holding the message text, and where one is there go on as for the `held` line, by branch 2 or 3 as the `nudged` line decides, and otherwise run no wake, which would start the role with no message, and put the sender's output to the owner as your next question; (2) the `held` line and `dctr-send: nudged <pane>` mean the role's first turn on the new model has started; (3) the `held` line and no `nudged` line, as for a session a warned line names, mean you run `dctr-send.mjs wake <role>`, since that wake types the nudge the send held; (4) after that wake, `dctr-send: woke <pane>: ` followed by what it typed means the turn has started, and no `woke` line means you put to the owner as your next question the role's name and the wake's output, since the role has no turn on his model; (5) a `dctr-send: no relay line written: <why>` line, which the sender prints with a non-zero exit while it still holds, nudges or wakes, means only that the `relay:` line E15 Messages has it append is missing, so write that line in your record yourself or, where you cannot, put it to the owner, and never resend or wake on it. The message goes first so that turn finds it in the held folder, and the wake follows only a held nudge so the role is not started twice. The message tells the role to run, as the first step of that turn, the capacity command its brief names, at its current tier, and to act on its output as the brief says. Never send the message or wake the role before the owner has typed `/model`, since its nudge would start a turn on the limited model. When the role's `question` report holds a `refuse` line, put it to the owner as your next question, with a tier or another model to recommend. Where he answers with a tier, send the role a message telling it to write, as its first action, `auto-cycle: on cap <its current cap> tier <his tier>`, which the role writes itself and you never write, and then to run the capacity command at that tier. Where he answers with another model, switch it in the order above.
- **An account-wide usage limit**: switch no model. The Recovery section says what you do.

## Recovery

On every StopFailure in a session of the run the cycle hook appends one line to `<run>/limits.log`, its kind `account`, `model` or `other`, and the watcher raises one `limit` event per line. Nothing waits, holds or schedules on a reset time, and no session reads a reset file. After an account-wide usage-limit stop the owner rolls, and then `node <plugin root>/hooks/dctr-send.mjs wake-all <run>`, run once from any shell, wakes every session that stop left idle, you among them; the watcher's notification and its `limit <role> account` event name that command. No session wakes another by hand for that stop. On an account limit event you send nothing, wake nothing and start no wave, and you end your turn: the watcher's notification carries the event to the owner. A standing-pause event for an R9 paused line (`Claude API error: ...`) of a role whose latest `limits.log` line is `account`, with no later `woken` line for that role in `events.log`, gets no wake and no question from you, since `wake-all` answers that stop; every other standing pause, R9 for a `model` or `other` line among them, you handle as before. A standing-pause event for an R8 paused line (`session idle, waiting for you`), for the merge session, a lane or yourself, never becomes a question of yours: read that role's record, and where it has no `auto-cycle: warned` line after its latest `auto-cycle: cycle` line (anywhere, where it has none), note the pause and ask nothing; otherwise run `dctr-send.mjs wake <role>` once, and put to the owner any output of it with no `woke` line. Your own first action on a restart is your handoff's read of the last 20 lines of `<run>/events.log`, which writes no file, so `doctrine-resume` finds it done or due, never ambiguous (`doctrine-handoff`'s orchestrator profile). Every `unfinished`, `unwoken` or no-agent `skip` line `wake-all` writes, and every other standing-pause event the watcher writes but an R8's, goes to the owner as a question; a pane with no agent is reported, never relaunched, and the owner restarts it by hand.

## Merges and ordering

- **The merge session**, neither a lane nor you, works in its own worktree made by `dctr-lane.mjs create merge`, with its own record and memory chain, and merges one lane at a time with `git merge --no-ff` at the integration branch's tip, when you ask through the sender. Its brief says: run the merged-revision gate through `hooks/dctr-gate.mjs` as `sh -c 'date -u +%Y-%m-%dT%H:%M:%SZ; git rev-parse HEAD; <the tests>; s=$?; date -u +%Y-%m-%dT%H:%M:%SZ; exit $s'`; start no merge, and make no Write, Edit or Bash call other than reads of that gate's transcript and result, until its `.result` is written; leave the merge on the integration branch only when the result reads `exit=0` with no `capture=incomplete` line, report it landed, and otherwise reset the integration branch to the commit before the merge and report that.
- **Write your checked-in line only after that landed report**, its gate `exit=0` with no `capture=incomplete` line, and ask for the next merge only after it. A lane repaired after its merge merges again, and its last merge is the one the line names.
- **A later lane's Members line carries `after <lane> merged`**, which you alone write. Its session starts only after the earlier lane's checked-in line, from that checked-in revision. While the predecessor's gate has not passed, or when it ends Stopped, ships at an escalation or reopens, hold the later lane and tell the owner.
- **A running lane declared after another**: tell it through its held folder to commit its work, send a `report` naming its HEAD, and do nothing more until its next message. Only once its predecessor has landed and that HEAD report is in, run `dctr-lane.mjs reset <lane> <landed revision>`, which keeps the lane's own earlier work on a side branch, then send the lane that side branch's name, and the lane re-applies its commits from it.
- **Where the project file lives in the code repo**, your Shared-writes commits sit on your own branch, and after the last lane has landed you ask the merge session to merge that branch as it merges a lane.

## The no-code boundary

You and your seats change no tracked file in any checkout or worktree outside your allowed paths, by any tool, Bash and MCP tools included, and a file you commit counts as tracked. Your allowed paths are your record and every file under the Records path, `docs/PROJECT.md`, every file under `docs/epics/`, your memory file, every file under `docs/handoffs/`, and the `.doctrine/auto-cycle` files. `hooks/dctr-guard.mjs` refuses your Write, Edit and NotebookEdit calls anywhere else and logs each to `<run>/guard.log`. It does not see Bash or MCP writes, so this rule is what holds them. Keeping working state in claude-mem or graft, and research by you or your seats, are not work in this sense. Only you write `docs/PROJECT.md` and the epic records (`doctrine-project`, its orchestrated-run rule).

## Ending the run

Send each lane, before you archive it, and the merge session, after its last landed report, a message through `dctr-send.mjs send` saying the run has ended, and each time wait until that session's record's last state line is no longer Open. After the last lane has landed and the epic's state is written, run `node hooks/dctr-lanewatch.mjs stop` as the last step of the run.

## Red flags

- A refusal skipped because the run "obviously" has herdr, or a project file judged present because `runRoot` returned a run.
- A lane created before the merge session, or after `create merge` refused.
- A capacity verdict worked out in prose, a capacity command run for a role other than the one running it or for a model that role is not yet running, a role that starts work before its capacity line or carries on after a `refuse`, the owner told to wait for a report before he types `/model`, the model file written after the owner types `/model`, no message sent once he says he has typed it, no wake after a send that printed `held` and no `nudged`, a resend after a send that printed no `held` line, a wake run before the send or after a send that printed no `held` line whose message is not in the held folder, a wake that printed no `woke` line not put to the owner, a resend or wake decided by an exit code or a `no relay line written` line, that missing `relay:` line neither written nor put to the owner, a new `auto-cycle: on` line that drops the role's current cap, the message sent or the role woken before the owner has typed `/model`, a hold on a reset time for any limit, or a role's `refuse` line left as a dead end rather than your next question.
- A guard probe judged by the Write's error with no `guard.log` line read.
- Text typed into a lane's pane that is not one of the four fixed lines: a message, a hand-typed wake, or `/model`.
- A waiting question written as a `question:` line in your record, or quoted from memory rather than word for word.
- A `/model` answer recorded as a `ruling:` line, or a model switched on an account-wide limit.
- A send, wake or wave on an account limit event, a session woken by hand after an account-wide stop instead of by `wake-all`, or a wake or question for an R9 pause whose role's latest `limits.log` line is `account` with no `woken` after it.
- An alarm ruled by you because the diagnosis seemed clear.
- A worktree reset by hand, other than the merge session's rollback after a failed gate, or a lane reset before its HEAD report is in.
- A checked-in line written on the merge session's word alone, before its gate reads `exit=0`.
- A Monitor still armed at your ready line, so your Stop is held and the cycle never comes.
- A fix to a lane's code made by you or your seat through Bash, because the guard did not stop it.
