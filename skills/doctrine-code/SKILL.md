# Doctrine Code

General coding under the doctrine.

**REQUIRED BACKGROUND:** Read the `doctrine` skill first: it defines phases/waves, the red-team gate, the phase exit gate, simplification, and the fallbacks for missing prerequisite skills. Designated review skill for this wrapper: `matts-code-review`, inside the phase gate. Four things it needs that no other step of this flow supplies:

- **A fixed point, pinned by you.** Its first process step is "whatever the user said is the fixed point — if they didn't specify one, ask for it", so a gate that dispatches it bare stops and asks the user, twice a phase, every phase. Pin **the SHA the phase started from** (`git rev-parse HEAD` before wave 1), not `main` or the merge-base: against either of those it re-reviews every phase already closed and re-files their findings, which doctrine step 5 counts as *outstanding* against the pass you are in, so no pass can ever come clean.
- **A spec source.** With none it skips the Spec sub-agent and reports "no spec available", and the phase gate's designated review runs one axis of two. Step 1 produces that source; pass its path. Issue-referenced specs additionally need Matt's `docs/agents/issue-tracker.md` — where that file is missing, issue numbers in commit messages won't resolve, so hand it a path rather than a `#N`.
- **The standards as they read at the fixed point.** Its step 3 finds the repo's standards sources and its step 4 hands the Standards sub-agent their paths, which that seat reads in the changed tree, so a diff that loosens a standard is judged against the loosened one, where doctrine step 3 reads review guidance at the fixed point. Hand it the standards sources' contents as they read at the fixed point, pasted, or as a retained snapshot the seat can read with its own tools (each file as `git show <fixed point>:<path>` prints it, written beside the record and outside the diff), and tell it to hand its Standards sub-agent those in place of the paths. A revision id alone is not this: the seat still reads the files from the tree it runs in.
- **The hub's finding split.** Its Standards axis returns labelled judgement calls freely ("possible Feature Envy", a rename suggestion) on top of documented-standard breaches. Grade everything it returns by doctrine step 5's test and its three buckets: a suggestion you decline with a stated reason is non-blocking and never counts against the pass, and a naming or wording note that changes neither what the code does nor what it is for is not a finding, per step 5, whatever file it sits in. Treat them all as blocking and a thorough review grinds the phase into the round alarm, an undeclared change to the gate, which the hub permits only when stated.

## Flow

1. If there's a spec or tickets, ask the user only the questions the spec leaves open (doctrine step 1), then proceed. If there's none, run superpowers:brainstorming; its interview IS the questions step, don't interrogate twice. **Either way, write the settled requirements to a file before wave 1** (doctrine step 1: write the answers down where the work lands) — the existing spec's own path, or a new file under the project's `docs/`, `specs/` or `.scratch/`. Those three directories are not arbitrary: they are where `matts-code-review` looks for a spec, and finding nothing there its Spec sub-agent skips and reports "no spec available" — so on the brainstormed path, the path this wrapper explicitly supports, the phase gate's designated review checks the code against nothing the user asked for and reports clean on one axis of two. Hand that path to every review you dispatch, the file as it stood at wave 1: a later ruling goes in the run record, never into this file. **The run record (doctrine step 1) is a different file.** Where a project file tracks the phase, `doctrine-project` says where the record goes and how it stays out of version control. With no project file, the record goes under `.doctrine/records/` in the repo root, never under those three directories, where `matts-code-review` would read run state as the spec, and the line `/.doctrine/records/` goes on a line of its own in the file `git rev-parse --path-format=absolute --git-path info/exclude` prints in that repo, so no tracked file changes.
2. Execute per Matt Pocock's `implement` skill (read its SKILL.md from your host's skill directory, which the hub's host reference names, if installed; inline fallback — and this is the default whenever `implement` isn't installed, not an edge case: `tdd` at **test seams you name and get agreed before wave 1**. Add them to step 1's questions; nothing else in this flow produces them, and "pre-agreed" with no agreement step means each wave agent picks its own. Those seams are also the module contract: the exports two seats in separate worktrees must agree on are settled here, by you, before dispatch, since isolated seats cannot agree on a name at runtime and an agent that reads this as a testing rule alone will fix the contract anyway and not know it did. **Then put them in each wave agent's prompt — the seams that agent owns, test-first at those seams**: the wave agent is the one writing the tests, and seams agreed with the user, written to a file and handed only to reviews reach nobody who writes one. A wave agent's gates run in its own tree, so a seam that imports a module another seat is writing gets that module's agreed exports in the agent's tree as a stub, or goes out in a later wave once the module is integrated: never brief an agent to expect a gate to fail on a module it does not own, since a gate expected to fail hides the failure that matters. Then typecheck regularly, single test files regularly, full suite once at the end, review at the end). **`implement`'s last two lines — review, then commit — are this flow's steps 4 and 5, not the wave agent's**: a wave prompt carries neither. The review is step 4's gate. The commit is yours: a wave agent never commits on the branch the run ships from — in a shared tree it returns its diff uncommitted, in its own worktree it commits on the worktree's own branch and hands it to you — and what a gate pass reads must be committed on that branch before the pass opens: the integrated wave output, then every repair and simplification diff after it, because `matts-code-review` reads `git diff <fixed-point>...HEAD`, an empty diff fails it and an uncommitted repair is invisible to it while the diff still reads non-empty. Which branch carries those commits is the repo's delivery norm's call (step 5): read that norm before wave 1, not after the commits exist, and step 5 then decides what happens to them next. A driven run's builder, briefed from `implement` as written, committed to the session branch before gate pass 1 had run.
3. Split the plan into phases; run independent slices as parallel waves **per doctrine step 2's isolation rule, which you read there in full rather than from this line**. Disjoint files are the floor, not the bar, and the part this wrapper depends on is the rest of it: two agents on disjoint component files sharing one `.next` and one dev port both keep answering 200 while the second build overwrites the first, and the UI section's visual check below then passes on the other agent's build. Own worktree, own output directory, own port, dependencies hardlinked rather than symlinked.
4. Phase exit: simplification review (doctrine step 6), finished and committed before the pass's native checks start → native checks → `matts-code-review` → red team → loop to doctrine step 5's exit condition for this phase, with a simplification review of each repair before the pass that re-checks it. The red team's brief carries, beside what doctrine step 4 hands every reviewer seat:
   - **Its axes**, each of which it must answer on: contract or seam breaks at the seams agreed before wave 1; an agreed seam with no test; behaviour that differs from the spec file as it stood at wave 1; anything duplicating a module or component already in the tree, which the designated review cannot see because it reads the diff; and breaches of the project's documented law.
   - **Step 1's requirements file**, holding the seams agreed before wave 1, as it stood at wave 1.
   - **The standards sources the designated review gets** (above): the standards sources' contents as they read at the fixed point, pasted, or as a retained snapshot the seat can read with its own tools.
   - **The smell baseline, by path**: the absolute path of the installed `matts-code-review` SKILL.md, under your host's skill directory, which the hub's host reference names, with an instruction to Read the smell baseline in its step 3. A smell from that baseline is a judgement call and is non-blocking unless doctrine step 5's blocking test independently holds. Where that file is not on disk, the seat runs on the standards sources alone and the report says so.
   - **The test-first standard the wave agents worked to**, as data: `implement`'s SKILL.md by absolute path where step 2 read it, otherwise step 2's inline fallback, `tdd` at the agreed seams. The seat grades the work against that standard and never runs it: it neither implements, reviews through sub-seats nor commits, whatever that method's own last steps say.
   - **On UI work**, what the UI section below adds to it.
5. Deliver per the repo's norms (doctrine step 7): commit — then **push and open a PR only where that norm says to, or where the user has said to.** Some repos' convention is explicitly the opposite, and where nothing documents a norm there is nothing to defer to: commit locally and ask.

## UI work

Same flow, plus the following — **and put it in each wave agent's prompt, not only here. The agent that styles the component is a wave agent; a rule sitting where only the dispatcher reads it reaches nobody who writes CSS.** One line in it needs resolving before you paste: the visual check names the `run` skill, and a skill name resolves to nothing from inside a seat — put the project's actual launch command (or the check's concrete steps) into the prompt beside the block, or the check degrades silently to whatever browser tooling the seat happens to have. Where the project cannot run authenticated UI locally there is no command to resolve, and the block's post-deploy branch must not fan out — N seats verifying one deployed surface is the shared-environment failure step 2 forbids — so the visual check becomes yours, run once against the documented post-deploy path after integration, and each wave agent's prompt says the visual check is deferred to integration.

Reuse the project's existing UI color patterns, component library, and layout conventions: grep for a sibling component before styling anything new, and **return the grep you ran** alongside the work, since the dispatcher has no other way to know what was searched for. Left in this file, four wave agents each style from scratch and the run ships four button treatments plus a duplicate of a component that already existed — and the phase gate won't catch the second one: `matts-code-review` reads the diff, so a component the diff duplicates from elsewhere in the tree is outside what its Standards axis can see. Verify visually with the `run` skill or browser tools before claiming done; tests alone don't prove UI. If the project can't run authenticated UI locally, say so and use its documented post-deploy verification path instead of skipping the visual check.

The red team's brief (step 4) on UI work also carries the reuse rule above, every wave agent's returned grep, and the renders or visual check output the producing side verified, a wave agent's or, where the check was deferred to integration, yours. The grep is the only record of what was searched before styling, and handed the diff alone the red team judges the code and not the result the builder claimed.

## Red flags

- Two wave agents on disjoint files, one `.next` and one port — and a screenshot taken as proof, showing the other agent's build.
- A wave agent that styled from scratch because the reuse rule stayed in this file and never entered its prompt.
- `matts-code-review` dispatched with no fixed point: it stops and asks the user mid-phase, or it takes `main` and re-files the findings of phases that closed last week.
- Requirements from a brainstorm that live only in the conversation, and a Spec axis reporting "no spec available" while the gate reads clean.
- A naming suggestion treated as blocking, so no pass comes clean and the phase grinds to the round alarm.
- `tdd` started at seams nobody agreed, each agent's guess different.
- UI declared done on green tests, with nothing rendered.
- Pushed, or a PR opened, with no repo norm and no instruction saying to.
